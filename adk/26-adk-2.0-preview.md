# 26 — ADK 2.0 Preview: Graph Workflows & Collaborative Agents

> **Official docs:** [ADK 2.0](https://google.github.io/adk-docs/2.0/) | **Status:** Alpha — not for production | **Install:** `pip install google-adk --pre`

## At a Glance

```
ADK 2.0 adds three new capabilities on top of 1.x:
│
├── Graph-Based Workflows
│   └── Deterministic routing through explicit node/edge graphs
│       (replaces LLM-driven routing for predictable flows)
│
├── Collaborative Agents
│   └── Coordinator + subagent teams with 3 operating modes:
│       chat (full interaction), task (autonomous), single_turn (parallel)
│
└── Dynamic Workflows
    └── Programmatic control with loops, conditionals, checkpointing
        (async/await patterns instead of static graphs)
```

ADK 2.0 is an **alpha release** adding graph-based workflows, collaborative agent teams, and dynamic workflows to the existing 1.x foundation. It is backward-compatible with 1.x agents but may have incompatibilities with advanced implementations. **Do NOT share storage (sessions, memory, evals) between 1.x and 2.0 projects.**


## Graph-Based Workflows

> **Official docs:** [Graph Workflows](https://google.github.io/adk-docs/workflows/)

Nodes are agents, tools, or plain functions. Edges define the execution graph. Routing is deterministic — **code decides the path, not the LLM**.

```python
from google.adk import Agent, Workflow, Event

# Nodes can be agents, functions, or tools
process_agent = Agent(
    name="processor",
    model="gemini-2.5-flash",
    instruction="Analyze the input and classify it.",
    output_schema=str,
)

def router_function(node_input: str):
    """Deterministic routing based on agent output."""
    if "urgent" in node_input.lower():
        return Event(message="Routing to urgent handler", route=["URGENT"])
    return Event(message="Routing to normal handler", route=["NORMAL"])

# Graph definition: nodes + edges
workflow = Workflow(
    name="triage_workflow",
    edges=[
        ("START", process_agent, router_function),
        (router_function, {
            "URGENT": urgent_handler,
            "NORMAL": normal_handler,
        }),
    ],
)
```

### [ ] When to use Graph vs 1.x agents

```
Use Graph-Based Workflows when:
├── You need deterministic routing (no LLM hallucination risk)
├── The process has well-defined steps and branches
├── You want to mix code logic with AI reasoning
└── Compliance/audit requires predictable execution paths

Use 1.x LlmAgent + AutoFlow when:
├── Routing decisions require understanding user intent
├── The agent tree is dynamic (sub-agents discovered at runtime)
├── You want the LLM to decide which specialist to use
└── The problem is open-ended (chat, Q&A, creative tasks)
```

## Collaborative Agents

> **Official docs:** [Collaborative Agents](https://google.github.io/adk-docs/workflows/collaboration/)

A coordinator agent delegates tasks to subagents. Three operating modes control how subagents interact:

```
Subagent Modes:
│
├── chat
│   ├── Full user interaction (questions, clarifications)
│   ├── Manual return via transfer_to_agent
│   └── NOT parallel — blocks the coordinator
│
├── task
│   ├── Autonomous execution with clarification questions
│   ├── Automatic return via complete_task()
│   ├── Cannot have sub-agents of its own
│   └── NOT parallel — runs sequentially
│
└── single_turn
    ├── No user interaction at all
    ├── Automatic immediate return
    ├── Each agent gets its own isolated session branch
    └── CAN run in parallel with other single_turn agents
```

```python
weather_agent = Agent(
    name="weather_checker",
    mode="single_turn",  # NEW in 2.0
    tools=[get_weather, geocode_address],
)

flight_agent = Agent(
    name="flight_finder",
    mode="task",  # autonomous, returns when done
    tools=[search_flights, book_flight],
)

coordinator = Agent(
    name="travel_planner",
    sub_agents=[weather_agent, flight_agent],
    # Coordinator automatically delegates and collects results
)
```

### [ ] Key difference from 1.x transfer

```
1.x transfer_to_agent:
├── LLM decides which agent to call
├── No structured return — agent just finishes
├── No parallel execution within a transfer
└── All agents share the same branch (no isolation)

2.0 collaborative modes:
├── Coordinator orchestrates delegation
├── task/single_turn agents return automatically
├── single_turn agents run in parallel with branch isolation
└── Structured input/output schemas for data flow
```

## Dynamic Workflows

> **Official docs:** [Dynamic Workflows](https://google.github.io/adk-docs/workflows/dynamic/)

For complex logic that doesn't fit a static graph — use Python control flow directly.

```python
from google.adk import node, Context, Event

@node(name="checker")
async def check_code(ctx: Context, code: str) -> dict:
    """Run linting and return findings."""
    return {"findings": ["unused import", "missing docstring"]}

@node(name="fixer")
async def fix_code(ctx: Context, finding: str) -> str:
    """Fix a single code issue."""
    return f"Fixed: {finding}"

@node(rerun_on_resume=True)
async def review_workflow(ctx: Context, node_input: str) -> str:
    """Dynamic workflow with loop + conditional."""
    # Step 1: Check code
    check_result = await ctx.run_node(check_code, input_data=node_input)

    # Step 2: Loop over findings (standard Python loop)
    for finding in check_result["findings"]:
        fix_result = await ctx.run_node(fix_code, input_data=finding)
        yield Event(state={"last_fix": fix_result})

    # Step 3: Parallel execution with asyncio
    import asyncio
    tasks = [ctx.run_node(validator, input_data=f) for f in check_result["findings"]]
    results = await asyncio.gather(*tasks)

    return f"All {len(results)} issues resolved"
```

### [ ] Key features

```
Dynamic Workflows:
├── @node decorator wraps functions into workflow nodes
├── ctx.run_node() executes child nodes with automatic checkpointing
├── Successful sub-nodes are automatically SKIPPED on resume
├── Standard Python loops, conditionals, recursion all work
├── asyncio.gather() for parallel node execution
└── Human input via RequestInput (pauses workflow for user response)
```
