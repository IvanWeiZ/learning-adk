# 25 — ADK 2.0 Preview: Graph Workflows & Collaborative Agents

> **Official docs:** [ADK 2.0](https://google.github.io/adk-docs/2.0/) | **Source:** `pip install google-adk --pre` | **Prereqs:** none

## At a Glance

```
ADK 2.0 adds three new capabilities on top of 1.x:
│
├── Graph-Based Workflows
│   └── Deterministic routing through explicit node/edge graphs
│       (replaces LLM-driven routing for predictable flows)
│
├── Collaborative Agents
│   └── Coordinator + subagent teams with 3 operating modes:
│       chat (full interaction), task (autonomous), single_turn (parallel)
│
└── Dynamic Workflows
    └── Programmatic control with loops, conditionals, checkpointing
        (async/await patterns instead of static graphs)
```

ADK 2.0 is an **alpha release** adding graph-based workflows, collaborative agent teams, and dynamic workflows to the existing 1.x foundation. It is backward-compatible with 1.x agents but may have incompatibilities with advanced implementations. **Do NOT share storage (sessions, memory, evals) between 1.x and 2.0 projects.**

## Graph-Based Workflows

> **Official docs:** [Graph Workflows](https://google.github.io/adk-docs/workflows/)

Nodes are agents, tools, or plain functions. Edges define the execution graph. Routing is deterministic — **code decides the path, not the LLM**.

### [ ] Sequential workflow

Edges are tuples — items execute left to right, each node's output feeds the next node's input.

```python
from google.adk import Agent, Workflow, Event
from pydantic import BaseModel

city_generator_agent = Agent(
    name="city_generator_agent",
    model="gemini-2.5-flash",
    instruction="Return the name of a random city. Return only the name.",
    output_schema=str,
)

class CityTime(BaseModel):
    time_info: str
    city: str

def lookup_time_function(node_input: str):
    return CityTime(time_info="10:10 AM", city=node_input)

city_report_agent = Agent(
    name="city_report_agent",
    model="gemini-2.5-flash",
    input_schema=CityTime,
    instruction="Output: It is {CityTime.time_info} in {CityTime.city} right now.",
    output_schema=str,
)

def completed_message_function(node_input: str):
    return Event(message=f"{node_input}\n WORKFLOW COMPLETED.")

root_agent = Workflow(
    name="root_agent",
    edges=[
        ("START", city_generator_agent, lookup_time_function,
         city_report_agent, completed_message_function)
    ],
)
```

### [ ] Conditional routing

A router function returns `Event(route=[...])` to pick which branch to follow. The next edge maps route strings to destination nodes.

```python
process_message = Agent(
    name="process_message",
    model="gemini-2.5-flash",
    instruction="Classify user message into 'BUG', 'CUSTOMER_SUPPORT', or 'LOGISTICS'.",
    output_schema=str,
)

def router(node_input: str):
    """Deterministic routing — code decides, not LLM."""
    routes = [r.strip() for r in node_input.split(",")]
    return Event(route=routes)

def handle_bug():
    return Event(message="Routing to bug handler...")

def handle_support():
    return Event(message="Routing to customer support handler...")

def handle_logistics():
    return Event(message="Routing to logistics handler...")

root_agent = Workflow(
    name="routing_workflow",
    edges=[
        ("START", process_message, router),
        (router, {
            "BUG": handle_bug,
            "CUSTOMER_SUPPORT": handle_support,
            "LOGISTICS": handle_logistics,
        })
    ],
)
```

```
Execution flow:
│
├── START
│   user message enters the workflow
│
├── process_message (Agent)
│   LLM classifies input → "BUG", "CUSTOMER_SUPPORT", or "LOGISTICS"
│
├── router (function)
│   reads classification string, returns Event(route=["BUG"])
│
└── route dispatch (dict)
    ├── "BUG"              → handle_bug
    ├── "CUSTOMER_SUPPORT" → handle_support
    └── "LOGISTICS"        → handle_logistics
```

### [ ] Multi-route fan-out

A router can return **multiple routes** — all matched branches execute:

```python
def multi_router(node_input: str):
    """Route to multiple handlers simultaneously."""
    return Event(route=["BUG", "LOGISTICS"])  # both fire
```

### [ ] Error handling in graph nodes

Wrap node functions with try/except and return structured errors via Event:

```python
from pydantic import BaseModel

class NodeResult(BaseModel):
    success: bool
    data: str | None = None
    error: str | None = None

def safe_api_call(node_input: str) -> NodeResult:
    """Node with built-in error handling."""
    try:
        result = call_external_api(node_input)
        return NodeResult(success=True, data=result)
    except TimeoutError:
        return NodeResult(success=False, error="API timeout")
    except Exception as e:
        return NodeResult(success=False, error=str(e))

def error_router(node_input: NodeResult):
    """Route based on success/failure."""
    if node_input.success:
        return Event(route=["SUCCESS"])
    return Event(route=["FAILURE"])

root_agent = Workflow(
    name="error_handling_workflow",
    edges=[
        ("START", safe_api_call, error_router),
        (error_router, {
            "SUCCESS": process_result,
            "FAILURE": handle_error,
        })
    ],
)
```

```
Error handling flow:
│
├── safe_api_call
│   wraps external call in try/except
│   returns NodeResult(success=True/False)
│
├── error_router
│   inspects NodeResult.success
│   returns Event(route=["SUCCESS"]) or Event(route=["FAILURE"])
│
└── route dispatch
    ├── "SUCCESS" → process_result (continue pipeline)
    └── "FAILURE" → handle_error (log, retry, notify)
```

### [ ] Loops via graph edges

ADK 2.0 graph workflows are DAGs by design — for true loops, use dynamic workflows (see below). If you need loop-like behavior in a graph, chain a router that re-enters the same sequence conditionally.

### [ ] When to use Graph vs 1.x agents

```
Use Graph-Based Workflows when:
├── You need deterministic routing (no LLM hallucination risk)
├── The process has well-defined steps and branches
├── You want to mix code logic with AI reasoning
└── Compliance/audit requires predictable execution paths

Use 1.x LlmAgent + AutoFlow when:
├── Routing decisions require understanding user intent
├── The agent tree is dynamic (sub-agents discovered at runtime)
├── You want the LLM to decide which specialist to use
└── The problem is open-ended (chat, Q&A, creative tasks)
```

## Collaborative Agents

> **Official docs:** [Collaborative Agents](https://google.github.io/adk-docs/workflows/collaboration/)

A coordinator agent delegates tasks to subagents. Three operating modes control how subagents interact.

### [ ] Mode comparison

```
Subagent Modes:
│
├── chat (default)
│   ├── Full user interaction (questions, clarifications)
│   ├── Manual return via transfer_to_agent
│   ├── Agent controls execution until explicit handoff
│   └── NOT parallel — blocks the coordinator
│
├── task
│   ├── Autonomous execution with optional clarification questions
│   ├── Automatic return via complete_task()
│   ├── Cannot have sub-agents of its own (leaf agent only)
│   └── NOT parallel — runs sequentially
│
└── single_turn
    ├── No user interaction at all
    ├── Automatic immediate return after one LLM call
    ├── Each agent gets its own isolated session branch
    └── CAN run in parallel with other single_turn agents
```

### [ ] Chat mode — full conversation handoff

The subagent takes over the conversation entirely. It can ask the user questions, receive answers, and keeps running until it explicitly calls `transfer_to_agent` to return control.

```python
from google.adk.workflow.agents.llm_agent import Agent

# Chat mode: agent takes full control of the conversation
support_agent = Agent(
    name="support_agent",
    mode="chat",  # default mode — can omit
    model="gemini-2.5-flash",
    instruction="""You are a support specialist. Ask the user clarifying
    questions to diagnose their issue. When resolved, transfer back to
    the coordinator using transfer_to_agent('coordinator').""",
    tools=[search_kb, create_ticket],
)

coordinator = Agent(
    name="coordinator",
    model="gemini-2.5-flash",
    instruction="Route support requests to support_agent.",
    sub_agents=[support_agent],
)
```

```
Chat mode execution:
│
├── User sends message → coordinator
│
├── Coordinator delegates → support_agent
│   (support_agent now owns the conversation)
│
├── support_agent ↔ User
│   multiple turns of Q&A, agent asks clarifications
│
├── support_agent calls transfer_to_agent("coordinator")
│   (explicit manual return)
│
└── Coordinator resumes control
```

### [ ] Task mode — autonomous with auto-return

The subagent runs autonomously. It can ask the user for clarification but automatically returns to the parent via `complete_task()` when done. Must be a leaf agent (no sub-agents).

```python
from pydantic import BaseModel

class ResearchResult(BaseModel):
    summary: str
    sources: list[str]
    confidence: float

# Task mode: runs autonomously, returns structured result
research_agent = Agent(
    name="research_agent",
    mode="task",
    model="gemini-2.5-flash",
    instruction="""Research the given topic thoroughly. Use search tools to
    gather information. When done, call complete_task() with your findings.
    If you need clarification from the user, ask — but finish autonomously.""",
    input_schema=str,
    output_schema=ResearchResult,
    tools=[web_search, summarize_page],
)

coordinator = Agent(
    name="coordinator",
    model="gemini-2.5-flash",
    instruction="Delegate research requests to research_agent.",
    sub_agents=[research_agent],
)
```

```
Task mode execution:
│
├── Coordinator delegates → research_agent
│   (passes input_schema data)
│
├── research_agent runs autonomously
│   ├── calls tools (web_search, summarize_page)
│   ├── may ask user for clarification (optional)
│   └── calls complete_task() when finished
│
├── Automatic return to coordinator
│   (output_schema ResearchResult sent back)
│
└── Coordinator receives structured result
```

### [ ] Single-turn mode — parallel, isolated, instant

Each agent gets exactly one LLM call. No user interaction. Runs in an isolated session branch. Multiple `single_turn` agents can execute in parallel.

```python
# Single-turn mode: one shot, no interaction, parallelizable
weather_agent = Agent(
    name="weather_checker",
    mode="single_turn",
    model="gemini-2.5-flash",
    instruction="Get the current weather for the user's location.",
    tools=[get_weather, geocode_address],
)

news_agent = Agent(
    name="news_checker",
    mode="single_turn",
    model="gemini-2.5-flash",
    instruction="Get the top 3 news headlines.",
    tools=[fetch_news],
)

stock_agent = Agent(
    name="stock_checker",
    mode="single_turn",
    model="gemini-2.5-flash",
    instruction="Get the current price of the user's watched stocks.",
    tools=[get_stock_price],
)

# All three single_turn agents can run in parallel
coordinator = Agent(
    name="morning_briefing",
    model="gemini-2.5-flash",
    instruction="""Create a morning briefing. Delegate to weather_checker,
    news_checker, and stock_checker simultaneously, then combine results.""",
    sub_agents=[weather_agent, news_agent, stock_agent],
)
```

```
Single-turn mode execution:
│
├── Coordinator delegates to all three agents
│
├── Parallel execution (isolated session branches)
│   ├── weather_checker → get_weather() → result
│   ├── news_checker    → fetch_news()  → result
│   └── stock_checker   → get_stock_price() → result
│
├── All three return automatically (one LLM call each)
│
└── Coordinator receives all results, composes briefing
```

### [ ] Context behavior: workflow node vs LlmAgent transfer

The same subagent behaves differently depending on where it is used:

```
As a workflow graph node:
├── Control advances to the NEXT graph node after completion
└── The workflow graph determines what happens next

As an LlmAgent sub_agent (transfer):
├── Control returns to the ORIGINATING agent
└── The parent coordinator decides what happens next
```

This means you can reuse the same agent in both contexts without modification.

### [ ] Key difference from 1.x transfer

```
1.x transfer_to_agent:
├── LLM decides which agent to call
├── No structured return — agent just finishes
├── No parallel execution within a transfer
└── All agents share the same branch (no isolation)

2.0 collaborative modes:
├── Coordinator orchestrates delegation
├── task/single_turn agents return automatically
├── single_turn agents run in parallel with branch isolation
└── Structured input/output schemas for data flow
```

## Dynamic Workflows

> **Official docs:** [Dynamic Workflows](https://google.github.io/adk-docs/workflows/dynamic/)

For complex logic that doesn't fit a static graph — use Python control flow directly.

### [ ] The @node decorator

Wraps a function into a workflow node with automatic checkpointing:

```python
from google.adk import node, Context, Event

@node(name="checker")
async def check_code(ctx: Context, code: str) -> dict:
    """Run linting and return findings."""
    return {"findings": ["unused import", "missing docstring"]}
```

Alternative: `FunctionNode` for wrapping without decorators:

```python
from google.adk import FunctionNode

def my_function(node_input: str):
    return f"Processed: {node_input}"

my_node = FunctionNode(
    my_function,
    name="processor",
    rerun_on_resume=True,
)
```

### [ ] ctx.run_node() — execute and return

`ctx.run_node()` executes a child node and **returns its output directly** — no manual state management needed:

```python
@node(rerun_on_resume=True)
async def pipeline(ctx: Context, user_request: str) -> str:
    # Each run_node returns the child's output directly
    raw_draft = await ctx.run_node(draft_agent, user_request)
    formatted  = await ctx.run_node(format_function, raw_draft)
    reviewed   = await ctx.run_node(review_agent, formatted)
    return reviewed
```

### [ ] Loops with standard Python

Use `while`/`for` loops — the framework handles checkpointing automatically:

```python
@node(rerun_on_resume=True)
async def code_review_loop(ctx: Context, code: str) -> str:
    """Loop until code passes all checks."""
    check_resp = await ctx.run_node(compile_lint_check, code)

    while check_resp.findings:
        # Emit intermediate state for observability
        yield Event(state={"code": code, "findings": check_resp.findings})

        # Fix and re-check
        code = await ctx.run_node(fixer_agent, code)
        check_resp = await ctx.run_node(compile_lint_check, code)

    return code  # all checks passed
```

```
Loop execution:
│
├── compile_lint_check
│   returns findings: ["unused import", "missing docstring"]
│
├── LOOP iteration 1
│   ├── yield Event (state checkpoint)
│   ├── fixer_agent → fixes "unused import"
│   └── compile_lint_check → findings: ["missing docstring"]
│
├── LOOP iteration 2
│   ├── yield Event (state checkpoint)
│   ├── fixer_agent → fixes "missing docstring"
│   └── compile_lint_check → findings: []
│
└── RETURN clean code
    (loop condition false, exit)
```

### [ ] Checkpointing and resume

Successful sub-nodes are **automatically skipped** when a workflow resumes. The `rerun_on_resume` parameter controls the parent node:

```python
@node(rerun_on_resume=True)
async def resilient_pipeline(ctx: Context, data: str) -> str:
    """If this workflow crashes after step 2, on resume:
    - step_1 is SKIPPED (already succeeded, checkpointed)
    - step_2 is SKIPPED (already succeeded, checkpointed)
    - step_3 re-runs from where it left off
    """
    result_1 = await ctx.run_node(step_1, data)       # checkpointed
    result_2 = await ctx.run_node(step_2, result_1)    # checkpointed
    result_3 = await ctx.run_node(step_3, result_2)    # re-runs on resume
    return result_3
```

```
Resume behavior:
│
├── rerun_on_resume=True on parent
│   parent function re-executes from the top
│
├── ctx.run_node(step_1, ...)
│   SKIPPED — checkpoint found, returns cached result
│
├── ctx.run_node(step_2, ...)
│   SKIPPED — checkpoint found, returns cached result
│
├── ctx.run_node(step_3, ...)
│   EXECUTES — no checkpoint, runs fresh
│
└── Workflow completes
```

### [ ] Execution IDs for checkpointing

The framework generates deterministic IDs based on parent ID + counter. You can provide custom IDs for named tasks:

```python
@node(rerun_on_resume=True)
async def process_orders(ctx: Context, orders: list) -> list:
    results = []
    for order in orders:
        # Custom name ensures stable checkpoint identity
        result = await ctx.run_node(
            process_single_order,
            order,
            name=order.order_id,  # deterministic ID
        )
        results.append(result)
    return results
```

**Warning:** Custom execution IDs must be deterministic. Non-deterministic IDs (e.g., UUIDs) break resume behavior.

### [ ] Human-in-the-loop with RequestInput

`RequestInput` pauses the workflow and waits for user input. Combined with a `BaseNode` subclass:

```python
from google.adk import BaseNode, RequestInput, Context
from typing import AsyncGenerator, Any

class GetInput(BaseNode):
    """Node that pauses workflow for user input."""
    rerun_on_resume = False  # don't re-ask on resume

    def __init__(self, request: RequestInput, name: str):
        self.request = request
        self.name = name

    async def run(self) -> AsyncGenerator[Any, None]:
        yield self.request

@node(rerun_on_resume=True)
async def approval_workflow(ctx: Context, proposal: str) -> str:
    """Workflow that pauses for human approval."""
    # Step 1: AI generates a summary
    summary = await ctx.run_node(summarize_agent, proposal)

    # Step 2: Pause and ask human for approval
    request = RequestInput(message=f"Approve this summary?\n\n{summary}\n\n(Yes/No)")
    user_response = await ctx.run_node(
        GetInput(request, "approval_step")
    )

    # Step 3: Branch based on human response
    if user_response.lower() == "yes":
        return await ctx.run_node(publish_agent, summary)
    else:
        return "Publication cancelled by reviewer."
```

```
Human-in-the-loop flow:
│
├── summarize_agent runs
│   produces summary text
│
├── GetInput("approval_step")
│   ├── yields RequestInput → workflow PAUSES
│   ├── user sees: "Approve this summary? (Yes/No)"
│   └── user responds → workflow RESUMES
│
├── rerun_on_resume=False on GetInput
│   user's response is cached, not re-asked on resume
│
└── Branch on user response
    ├── "yes" → publish_agent
    └── "no"  → cancellation message
```

### [ ] Parallel node execution with asyncio.gather

Run multiple nodes concurrently using standard asyncio:

```python
import asyncio
from google.adk import node, Context, BaseNode
from typing import Any

# Pattern 1: Direct asyncio.gather in a workflow node
@node(rerun_on_resume=True)
async def parallel_analysis(ctx: Context, document: str) -> dict:
    """Run three analyses in parallel."""
    sentiment_task = ctx.run_node(sentiment_agent, document)
    summary_task   = ctx.run_node(summary_agent, document)
    entities_task  = ctx.run_node(entity_extractor, document)

    sentiment, summary, entities = await asyncio.gather(
        sentiment_task, summary_task, entities_task
    )

    return {
        "sentiment": sentiment,
        "summary": summary,
        "entities": entities,
    }

# Pattern 2: Reusable ParallelNode for dynamic fan-out
class ParallelNode(BaseNode):
    """Execute a node against multiple inputs in parallel."""

    def __init__(self, inner_node: BaseNode, name: str = "parallel"):
        self.inner_node = inner_node
        self.name = name

    async def run(self, ctx: Context, node_input: list[Any]):
        tasks = [ctx.run_node(self.inner_node, item) for item in node_input]
        return await asyncio.gather(*tasks)

# Usage:
parallel_validator = ParallelNode(validate_item, name="parallel_validate")

@node(rerun_on_resume=True)
async def batch_workflow(ctx: Context, items: list[str]) -> list:
    return await ctx.run_node(parallel_validator, items)
```

## Migration Checklist: 1.x to 2.0

Step-by-step guide for moving an existing 1.x project to 2.0.

### [ ] Pre-migration

```
1. Environment check
│
├── Verify Python version >= 3.11
│   python3 --version
│
├── Create a NEW virtual environment
│   python3 -m venv .venv-2.0 && source .venv-2.0/bin/activate
│
├── Install ADK 2.0 alpha
│   pip install google-adk --pre
│
└── NEVER install 2.0 in the same venv as 1.x
```

### [ ] Storage isolation

```
2. Isolate storage (CRITICAL)
│
├── Create new session storage
│   do NOT point at existing 1.x session databases
│
├── Create new memory storage
│   1.x and 2.0 memory formats are incompatible
│
├── Create new eval datasets if needed
│   eval schemas may differ
│
└── If using SQLite:
    use completely separate .db files
```

### [ ] Code compatibility

```
3. Test existing agents (no changes needed)
│
├── Run existing 1.x agents as-is
│   they should work without modifications
│
├── Watch for warnings/deprecations in console output
│   alpha may surface new warnings
│
├── Test all tool functions
│   tool registration API is unchanged
│
└── Test all callbacks (before/after agent, model, tool)
    callback signatures are unchanged
```

### [ ] Incremental adoption

```
4. Adopt 2.0 features incrementally
│
├── Start with one workflow — don't convert everything at once
│
├── Identify deterministic routing candidates
│   SequentialAgent → Workflow with sequential edges
│   Manual if/else routing → Workflow with conditional routing
│
├── Identify parallel candidates
│   ParallelAgent → still works, but single_turn mode adds isolation
│
├── Identify loop candidates
│   LoopAgent → Dynamic workflow with while loop
│
└── Keep LlmAgent + AutoFlow for open-ended routing
    don't replace working intent-based routing
```

### [ ] Testing

```
5. Validate before deploying
│
├── Run existing test suite — should pass unchanged
│
├── Add tests for new Workflow/dynamic nodes
│   test conditional routes hit the right branches
│   test loop termination conditions
│   test checkpoint/resume behavior
│
├── Test error paths
│   what happens when a node throws?
│   what happens when an LLM call fails mid-workflow?
│
└── Compare outputs between 1.x and 2.0 for same inputs
    regression check before cutover
```

## When NOT to Use 2.0

ADK 2.0 is not always the right choice. Stay on 1.x patterns when:

```
Stay on 1.x when:
│
├── Production stability required
│   2.0 is alpha — breaking changes are expected
│   no backward-compatibility guarantees between alpha releases
│
├── Python < 3.11
│   2.0 requires 3.11+, 1.x works with 3.10+
│   if your deployment is pinned to 3.10, you cannot use 2.0
│
├── Open-ended conversational agents
│   LlmAgent + AutoFlow is better for free-form chat
│   graph workflows add overhead for "just talk to the user" agents
│
├── Simple linear pipelines
│   SequentialAgent is simpler than Workflow for A → B → C
│   don't over-engineer with graphs when sequential works
│
├── Existing agent trees that work well
│   if transfer_to_agent routing is accurate enough, keep it
│   deterministic routing is for when LLM routing fails or is risky
│
├── Live streaming required
│   graph workflows are incompatible with Live Streaming
│   stick with 1.x agents for streaming use cases
│
├── Shared session state between agents
│   single_turn mode isolates session branches
│   if agents need to read each other's intermediate state, use chat mode
│   or stick with 1.x shared-branch transfer
│
└── Third-party integrations
    some integrations are not yet supported in 2.0
    check compatibility before migrating
```

### [ ] Decision tree

```
Should you use 2.0?
│
├── Is this a production system?
│   └── YES → Stay on 1.x until 2.0 is stable
│
├── Do you need deterministic routing?
│   └── YES → Use Graph-Based Workflows
│
├── Do you need parallel agents with isolation?
│   └── YES → Use single_turn mode (2.0)
│
├── Do you need loops with checkpointing?
│   └── YES → Use Dynamic Workflows
│
├── Do you need human-in-the-loop pauses?
│   └── YES → Use Dynamic Workflows + RequestInput
│
├── Is the routing open-ended / intent-based?
│   └── YES → Stay with LlmAgent + AutoFlow (1.x pattern)
│
└── Is it a simple sequential pipeline?
    └── YES → SequentialAgent (1.x) is simpler
```

## Migration Notes

| Topic | Detail |
|---|---|
| **Backward compatible** | 1.x agents work in 2.0 without changes |
| **Storage isolation** | **NEVER** share session/memory storage between 1.x and 2.0 projects |
| **Python version** | 2.0 requires Python 3.11+ (1.x works with 3.10+) |
| **Install** | `pip install google-adk --pre` (alpha, `--pre` required) |
| **Production** | Not recommended during alpha |
| **Incompatibilities** | Advanced/feature-rich agents may hit edge cases — report via GitHub |
